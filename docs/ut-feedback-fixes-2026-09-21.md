# 댓글·커피챗 보상 우선 수정

기준: 2026-09-21, main `a6589e2e`를 fast-forward pull한 뒤 작업.
관련 이슈: #296, #301. 이 PR은 프론트 배포 없이 서버 수정만으로 적용되는 범위다.

## 댓글 작성 500 (#296)

`V18__Expand_comment_content.sql`에서 `comments.content`를 TINYTEXT에서 TEXT로 확장하고 엔티티 정의도 맞춘다. 생성·수정 API의 5,000자 제한은 유지하며 기존 migration은 수정하지 않는다.

V18이 적용되어야 운영의 한글 86자 이상 댓글 저장 오류가 해결된다. H2 MySQL 모드로 기존 댓글 보존, 한글 85/86/5,000자와 이모지 저장·수정, DTO 5,001자 거절을 검증했다. 실제 MySQL 바이트 제한과 운영 migration 실행을 대체하는 검증은 아니다.

## 커피챗 보상 (#301)

UT 문서에 따라 **수락한 사용자에게 동일 상대 최초 1회 500P**를 지급한다. A가 B에게 요청하면 B가 받는다. 종료 후 같은 상대와 다시 수락해도 B에게 추가 지급하지 않는다. 반대 방향으로 A가 수락하면 A의 수령 이력을 별도로 판단한다.

- 키는 `COFFEECHAT_PAIR:{수령자ID}:{상대ID}`다. requestId는 거래 이력 추적값으로 유지한다.
- 수령자 지갑 잠금 안에서 과거 지급 확인과 새 지급을 수행하고, 고유 event_key로 동시 요청을 방어한다.
- 기존 requestId 방식으로 같은 상대에게서 받은 커피챗 보상도 최초 1회에 포함한다. 과거에 요청자로 받은 금액을 회수하거나 소급 보상하지 않는다.
- 재요청·재수락 자체는 허용하며 보상만 중복 지급하지 않는다.
- `/api/request/respond` 형식은 동일하다. 성공이 매번 500P 지급을 의미하지 않는다. 프론트 변경 전에도 중복 지급은 서버에서 차단한다.
- TEAM_RECRUIT는 공유 경로의 기존 요청별 보상을 유지한다.

## 프론트 전달 문장

> 서버에서 댓글 저장 500과 커피챗 중복 보상을 먼저 수정합니다. 배포 시 댓글 컬럼을 TEXT로 확장하며 기존 5,000자 제한을 유지합니다. 커피챗은 수락자에게 동일 상대 최초 1회만 500P를 지급합니다. 재수락 성공만으로 500P 적립을 표시하지 말고 수락 후 서버 잔액을 다시 조회해 주세요. 요청/수락 처리 중 중복 클릭을 막고 실패 후 버튼 상태를 복구해 주세요. 중복 요청 409/48901, 이미 열린 채팅방 409/48902도 구분해서 안내해 주세요. 이 프론트 작업은 서버 중복 지급 방지의 선행 조건은 아닙니다.

첨부 티켓 교체는 프론트가 실패한 fileKey를 전달해야 하므로 별도 후속 PR로 분리한다. 해당 PR에 replaceFileKeys 계약과 전달 예시를 제공한다.

## 삭제 댓글이 남는 이유 (#299)

`CommentServiceImpl.list()`는 PUBLISHED와 DELETED를 함께 조회하고 삭제된 본문을 ‘삭제된 댓글입니다.’로 바꾼다. 답글의 부모 자리 유지에 필요한 처리지만 살아 있는 답글이 없는 삭제 댓글까지 포함한다.

삭제 시 `decComment()`와 루트 댓글의 `decRootComment()`를 이미 호출한다. 화면 잔존과 댓글 수 미감소는 별도 문제이며, 후자는 API 응답·PostStats·프론트의 배열 길이 계산과 캐시 갱신을 대조해야 한다.

후속 방향은 살아 있는 답글이 있는 삭제 부모만 남기고 나머지 삭제 댓글은 DB 조회 조건에서 제외하는 것이다. 이번 PR에서는 조회 정책이나 운영 댓글 데이터를 바꾸지 않는다.
