# 댓글·커피챗 보상·커뮤니티 첨부 수정

기준: 2026-09-21, main `a6589e2e`를 fast-forward pull한 뒤 작업.
관련 이슈: #296, #301, #300. 삭제 댓글 잔존(#299)은 원인 설명만 포함한다.

## 서버 변경

### 댓글 작성 500 (#296)

`V18__Expand_comment_content.sql`에서 `comments.content`를 TINYTEXT에서 TEXT로 확장하고 엔티티 정의도 맞춘다. 생성·수정 API의 5,000자 제한은 유지한다. 기존 V0 등 이미 적용된 migration은 수정하지 않는다.

V18이 적용되어야 운영의 한글 86자 이상 댓글 저장 오류가 해결된다. TEXT는 5,000자의 UTF-8 본문을 수용한다. H2 MySQL 모드로 기존 댓글 보존, 한글 85/86/5,000자와 이모지의 저장·수정을 확인하며 DTO 5,001자 거절도 검증한다. H2 검증은 MySQL의 실제 TINYTEXT 바이트 제한이나 운영 migration 실행을 대체하지 않는다.

### 커피챗 보상 (#301)

UT 문서에 따라 **수락한 사용자에게, 동일 상대에 대해 최초 1회 500P**를 지급한다. A가 B에게 요청하면 B가 받는다. 종료 후 A가 B에게 재요청해도 B에게 추가 지급하지 않는다. B가 A에게 요청하고 A가 수락하는 경우 A의 수령 이력은 별도로 판단한다.

- 키: `COFFEECHAT_PAIR:{수령자ID}:{상대ID}`. requestId는 거래 이력의 추적값으로 남는다.
- 수령자 지갑 잠금 안에서 과거 지급 이력 확인과 새 지급을 수행하고, 고유 event_key로 동시·재시도를 방어한다.
- 기존 requestId 방식으로 같은 상대에게서 받은 커피챗 보상도 1회 수령에 포함한다. 과거에 잘못 요청자에게 지급한 금액을 회수하거나 소급 보상하지 않는다.
- 채팅방 종료 후 재요청/재수락 자체는 가능하다. 포인트를 중복 지급하지 않는 것이다.
- `/api/request/respond`의 요청·응답 형식은 동일하다. 성공 응답은 매번 500P 지급을 뜻하지 않는다.
- 같은 응답 경로를 쓰는 TEAM_RECRUIT의 기존 요청별 보상은 이번 변경 대상에서 제외하고 유지한다.

### 커뮤니티 첨부 재시도 (#300)

포트폴리오 썸네일의 ‘이전 미사용 티켓 만료 + 새 티켓 발급을 한 트랜잭션으로 처리’하는 방식을 재사용한다. 단, 커뮤니티는 최대 3개의 다건 첨부이므로 사용자 전체 티켓을 지우지 않고 **클라이언트가 실패/취소했다고 지정한 티켓만 교체**한다.

`POST /api/community/posts/uploads/presign`에 선택 필드 `replaceFileKeys`를 추가한다.

```json
{
  "items": [
    {"contentType": "image/png", "size": 12345, "originalFilename": "retry.png"}
  ],
  "replaceFileKeys": ["이전 presign 응답의 실패한 fileKey"]
}
```

- 미전송/null/빈 배열은 기존 추가 발급 동작이다. 정상 업로드한 파일을 보존하면서 실패한 것만 교체할 수 있다.
- 교체 키는 최대 3개이며, 본인 소유 COMMUNITY_POST_ATTACHMENT 목적의 미사용 티켓만 허용한다. 이미 EXPIRED인 티켓은 재시도 편의를 위해 허용한다.
- 다른 사용자/목적은 403/49310, USED는 400/49010, 존재하지 않는 키는 404/49410, 중복 키는 400/49022다. DTO 형식/길이 검증은 400/40000과 errors[]를 사용한다.
- 남아 있는 유효 티켓 수 + 새 파일 수가 3개를 넘으면 429/49006이다. 이 경우 기존 티켓 만료도 롤백된다.
- 새 파일 검증 실패, 서명 발급 실패 시 기존 티켓을 유지한다. USED, 다른 사용자·목적, 교체에 지정하지 않은 PENDING은 건드리지 않는다.
- 교체된 키는 더 이상 게시글 저장에 사용할 수 없다. 재시도에서는 새 응답의 fileKey/uploadUrl을 사용한다. S3 객체를 이 API에서 즉시 삭제하지는 않는다.
- **프론트 적용이 필요하다.** 기존 클라이언트가 replaceFileKeys 없이 계속 재발급하면 이전처럼 한도에 걸릴 수 있다. 응답을 잃어 키를 모르는 티켓까지 서버가 무조건 정리하지 않는다.

## 삭제 댓글이 남는 이유 (#299)

`CommentServiceImpl.list()`가 PUBLISHED와 DELETED를 함께 조회하고, 삭제된 본문을 ‘삭제된 댓글입니다.’로 바꾼다. 답글을 연결할 부모 자리 보존에 필요한 처리지만, 현재는 살아 있는 답글이 없는 삭제 댓글까지 그대로 포함한다.

삭제 메서드에서는 이미 `decComment()`와 루트 댓글의 `decRootComment()`를 호출한다. ‘화면에 삭제 댓글이 남음’과 ‘댓글 수가 감소하지 않음’은 별도 문제다. 후자는 실제 API 응답, PostStats, 프론트의 배열 길이 계산·캐시 갱신을 대조해야 한다.

후속 수정 방향은 ‘살아 있는 답글이 있는 삭제 부모만 남기고, 답글 없는 삭제 댓글과 삭제 답글은 숨기기’다. 페이지네이션 전에 DB 조회 조건에서 제외해야 한다. 이번 PR은 이 조회 정책이나 운영 댓글 데이터를 변경하지 않는다.
