# 포트폴리오 부제목과 기술 스택 저장 계약

적용 변경: `fix/portfolio-subtitle-tech-stack-contract` (2026-09-13).

## 부제목 수정

`PATCH /api/portfolio/{portfolioUserId}/{portfolioId}`에서 `subtitle`은 다음과 같이 처리한다.

| 요청 | 결과 |
|---|---|
| subtitle 미전송 | 저장된 부제목 보존 |
| `"subtitle": null` | 부제목 삭제 |
| `"subtitle": "새 부제목"` | 새 값으로 교체 |
| `"subtitle": ""` | 기존 계약대로 빈 문자열 저장 |

부제목 최대 길이는 50자다. 생성 시 부제목은 계속 선택값이다. 요청 DTO에서 JSON 필드 존재 여부를 추적하며, 내부 `subtitleProvided`는 외부 요청 값으로 설정할 수 없다. 다른 필드의 수정 의미와 소유권/계정 상태 검증은 기존 계약을 따른다.

## 기술 스택 길이

- 생성·수정 모두 `techStack`은 최대 10개, 항목당 최대 50자다.
- 공백뿐인 항목과 null 항목은 허용하지 않는다. 배열 자체의 미전송/null은 기존처럼 빈 목록으로 처리한다.
- 예: `["React, TypeScript, Tailwind CSS"]`는 20자를 넘는다는 이유로 거절되지 않는다.
- 현재 쉼표 저장 형식으로 최대 요청은 `10 × 50 + 9 = 509`자다. 엔티티와 DB 컬럼을 `VARCHAR(512) NOT NULL`로 맞춘다.

`V17__Expand_portfolio_tech_stack.sql`을 새로 추가한다. 적용된 V0–V16은 수정하지 않는다. 운영에서 50자 제한을 사용하는 서버를 기동할 때 Flyway V17이 먼저 적용되어야 한다. 기존 데이터는 그대로 유지된다.

배열 항목 안의 쉼표를 저장 후 다시 분리하는 기존 StringListConverter의 동작과 FE의 첫 기술 항목만 복원하는 문제는 별도 미해결 항목이다. 이번 변경은 길이 제한·저장 용량과 부제목 호환성을 처리한다.

## 검증

- 실제 controller → JSON 역직렬화/검증 → service 경로에서 부제목 미전송 보존, 명시적 null 삭제, 값 교체, 내부 표시값 조작 방지를 확인한다.
- 생성·수정에서 50자 기술 10개 허용, 51자/11개/잘못된 날짜 등 거절, 기존 필수값 검증을 확인한다.
- 생성된 OpenAPI에 내부 표시값이 노출되지 않고 기술 제한이 10개·50자로 표시되는지 확인한다.
- H2 MySQL 모드에서 실제 V17 SQL을 실행해 기존 데이터 유지와 509자 입력 저장·조회를 확인한다. 운영 MySQL 실행을 대체하는 검증은 아니다.

## 썸네일 업로드 재시도 (2026-09-14)

운영 로그에서 포트폴리오 수정의 `techStack[0]` 검증 실패(400) 직후 썸네일 presign 재시도가 429/49006으로 거절되는 것을 확인했다. 프론트는 썸네일을 먼저 업로드한 뒤 포트폴리오를 저장하며, 저장이 실패하면 재시도 때 presign을 다시 요청한다. 기존 서버는 사용자별 미사용 썸네일 티켓을 1개로 제한하므로 첫 요청의 티켓이 남아 있는 10분 동안 재시도가 막혔다.

- `POST /api/portfolio/{portfolioUserId}/uploads/presign/thumbnail`은 소유권·계정·파일 검증 후 해당 사용자의 이전 `PORTFOLIO_THUMBNAIL/PENDING` 티켓을 만료 처리하고 새 티켓을 발급한다.
- 사용자 행 잠금을 획득한 동일 트랜잭션에서 교체하므로 동시 발급은 직렬화되고, 발급 실패 시 이전 티켓의 만료 처리도 롤백된다. 유효한 미사용 썸네일은 최대 1개를 유지한다.
- 재발급 후에는 마지막 응답의 `fileKey`를 사용해야 한다. 여러 편집 창에서도 마지막 발급이 이전 미사용 썸네일을 대체한다. 이미 저장된 `USED` 티켓, 다른 사용자, 첨부파일·프로필 등 다른 목적의 티켓은 변경하지 않는다.
- S3 파일 자체는 이 단계에서 삭제하지 않는다. 이전 서명 URL은 원래 만료 시각까지 PUT이 가능하지만, 교체되어 만료된 티켓으로 포트폴리오를 저장할 수는 없다.
- 첨부파일 다건 업로드의 개수 제한과 다른 도메인의 업로드 정책은 기존대로 유지한다.

같은 시간대 Nginx access log의 405는 썸네일 presign 주소에 대한 **GET** 요청이었다. 해당 주소는 메타데이터를 받는 POST API이므로 GET의 405/40500은 정상이다. 파일 바이트는 presign 응답의 S3 `uploadUrl`로 **PUT**, 포트폴리오 수정은 **PATCH**로 전송한다. 조회한 프론트 코드도 이 메서드를 사용한다.

회귀 테스트는 실제 HTTP controller → service → PresignEngine → H2 DB와 개별 트랜잭션을 사용한다. S3 호출과 인증 컨텍스트는 테스트 대역으로 구성한다. 반복 발급·이미지 교체, 교체된 티켓 소비 차단, 기존 티켓 보호, 잘못된 파일과 타인 요청 거절, 발급 실패 롤백, GET 405를 검증한다.

## 제목 길이

생성·수정의 `projectTitle`은 필수이며 최대 20자다. 21자 이상은 `400 / 40000`으로 거절한다. 기존 제목은 자르지 않고 그대로 조회하며, 기존 글을 수정할 때는 제목을 20자 이내로 전송해야 한다. DB 컬럼 길이는 축소하지 않아 기존 데이터가 보존된다.
